INTEGRACAO DO FSR3 FRAME GENERATION NO CEMU-ANDROID (v3 - VULKAN)
====================================================================
Atualizado apos inspecionar o fsr3.zip real e descobrir a cadeia de
ferramentas DXC -> SPIRV-Cross. Esta versao CORRIGE um ponto errado
das versoes anteriores: para o backend VULKAN voce NAO precisa portar
os shaders para GLSL manualmente. Explicacao abaixo.

Escopo: apenas FSR3 Frame Generation (Optical Flow + Frame
Interpolation, nao-ML, aberto). Fora de escopo: FSR4, Upscaler de
resolucao, Ray Regeneration, CACAO, CAS, Blur, DoF, Lens, SSSR, SPD
(exceto o header de dependencia), Denoiser.


CORRECAO IMPORTANTE EM RELACAO AS VERSOES ANTERIORES
---------------------------------------------------------
Nas versoes v1/v2 deste relatorio eu disse que seria necessario
"portar os ~20 shaders de HLSL para GLSL" antes de integrar no
Vulkan. Isso estava errado. O Vulkan consome SPIR-V, nao GLSL - e o
dxc.exe (parte do Vulkan SDK) compila HLSL DIRETO para SPIR-V com a
flag -spirv, sem nenhuma reescrita manual de logica. Ou seja:

  Para VULKAN: dxc.exe -spirv converte o .hlsl -> .spv automaticamente.
               Nao ha "porte" manual de shader nenhum aqui.

  Para OPENGL: so ai sim entra o GLSL, pegando o MESMO .spv gerado
               acima e passando pelo spirv-cross.exe (ver o outro
               relatorio, "porte-opengl-framegen-cemu-android.txt").

Isso simplifica bastante o trabalho do lado Vulkan: o "porte de
shader" inteiro vira um laco de comando (ja documentado no arquivo
comandos-powershell-conversao-fsr3.txt), nao 20 reescritas manuais.

2. O QUE FAZER COM CADA GRUPO DE ARQUIVO
--------------------------------------------

PASSO A - Compilar os 20 .hlsl para SPIR-V (automatico, sem reescrita manual)
  Use os comandos ja prontos em comandos-powershell-conversao-fsr3.txt,
  secao "O QUE FAZER PARA O VULKAN". Resultado: pasta spv_output\ com
  20 arquivos .spv.

PASSO B - Carregar os .spv no seu backend Vulkan
  Cada .spv vira um VkShaderModule via vkCreateShaderModule. Nao
  precisa editar o conteudo do .spv.

PASSO C - Escrever o C++ que orquestra tudo (aqui SIM e trabalho manual)
  Usando os headers da secao 1.3 (structs) e a ordem de dispatch
  encontrada nos .cpp de referencia da secao 1.4, escreva:
  - opticalflow_vk.cpp: cria buffers intermediarios (luma, piramide,
    histograma, vetores), grava vkCmdDispatch na ordem correta com
    vkCmdPipelineBarrier entre cada pass.
  - frameinterpolation_vk.cpp: mesma logica, para o pipeline de
    interpolacao. Pule os dois shaders de motion vectors do jogo (nao
    chame o dispatch deles, mesmo tendo compilado o .spv).
  - swapchain_vk.cpp: substitui vkQueuePresentKHR/vkAcquireNextImageKHR
    para intercalar frame real -> interpolado -> real, baseado no
    padrao de FrameInterpolationSwapchainDX12_Helpers.cpp.

4. FLUXO DE INTEGRACAO NO RUNTIME
--------------------------------------

1. Inicializacao (uma vez, ao criar o device Vulkan):
   - Criar contexto de Optical Flow e de Frame Interpolation.
   - Substituir as chamadas de swapchain do Cemu pelas equivalentes
     do swapchain_vk.cpp.
2. A cada frame, antes do present:
   - Dispatch do Optical Flow (backbuffer atual + anterior, so cor).
   - Dispatch do Frame Interpolation (vetores do passo anterior +
     os dois backbuffers -> gera o frame intermediario).
   - Apresenta: real -> interpolado -> real -> interpolado (2x).
3. Encerramento: destruir os contextos ao fechar o jogo/emulador.


5. OPCOES A EXPOR PRO USUARIO DURANTE O JOGO
--------------------------------------------------
| Opcao                          | O que faz                         | Faixa sugerida |
|---------------------------------|------------------------------------|-----------------|
| Ativar/Desativar                | Liga/desliga instantaneamente     | on/off          |
| Multiplicador                   | Quantos frames gerar por real      | 2, 3, 4         |
| Flow scale                      | Resolucao interna da estimativa    | 0.5 - 1.0       |
| Modo performance                | Optical Flow mais leve             | on/off          |
| Limite de FPS base              | Trava o FPS real antes de gerar    | 30, 40, 60      |
| Perfil por jogo                 | Config salva por titulo            | -               |
| Mostrar so o frame interpolado  | Debug, comparacao de qualidade     | on/off (dev)    |
| Indicador FPS real vs. gerado   | Overlay de transparencia           | on/off          |

Prioridade sugerida: Ativar/Desativar -> Multiplicador -> Flow scale
-> Modo performance -> Limite de FPS -> Perfil por jogo. As duas
ultimas sao bonus, nao bloqueantes.


6. RISCOS
-------------
- Reconstrucao de depth sem depth real do jogo (dentro do pass
  ffx_frameinterpolation_reconstruct_and_dilate_pass) continua sendo o
  ponto mais arriscado tecnicamente - pode exigir ajuste de logica,
  nao so compilacao direta.
- Teste em GPU Adreno/Mali de gama baixa antes de assumir que o modo
  performance basta - o Optical Flow e a parte mais cara
  computacionalmente mesmo sem motion vectors do jogo.
- Pacing do present com 2 filas de apresentacao (real + gerado) pode
  gerar stutter dependendo do presentation mode do swapchain
  (Mailbox tende a funcionar melhor que FIFO aqui, custa mais bateria).
